# `25.json` — RECONSTRUCTED, not compiler-generated

## Status

**RECONSTRUCTED.** This file was **not** emitted by the Room KSP processor. It was produced by
`scripts/audit/reconstruct_v25.ps1` from the compiler-generated `26.json`.

## Why a reconstruction was necessary

`AppDatabase` declared `exportSchema = false` for the entire life of this database, so Room never
wrote a schema history. No `app/schemas/` directory existed and **no historical schema JSON was ever
committed to Git**. `MigrationTestHelper` can only create a database at a historical version if that
version's schema JSON exists.

Consequences:

- Version **26** is compiler-generated and authoritative.
- Versions **1–24** are **NOT RECONSTRUCTABLE** — their migrations contain DDL
  (`CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE INDEX`, `RENAME TO`) whose *pre-state* cannot
  be derived from the current entity classes without guessing. Reconstructing them would mean
  inventing a starting schema, which is forbidden.
- Version **25** **is** reconstructable, for the reason below.

## Why v25 ≡ v26 structurally

`MIGRATION_25_26` (`AppDatabase.kt:961`) contains **zero DDL statements**. It is eight `UPDATE`
statements and nothing else:

| # | Table | Operation |
|---|---|---|
| 1 | `circuits` | set `assignedGeneratorId` when exactly one generator exists |
| 2 | `circuits` | clear `generatorIncluded` when the count is ambiguous |
| 3 | `circuits` | set `assignedAtsId` when exactly one ATS exists |
| 4 | `circuits` | clear `atsIncluded` when the count is ambiguous |
| 5 | `circuits` | set `assignedUpsId` when exactly one UPS exists |
| 6 | `circuits` | clear `upsBacked` when the count is ambiguous |

Verified mechanically by `scripts/audit/classify_migrations.ps1`, which classifies all 25
migrations by DDL/DML content:

```
MIGRATION_25_26  25->26  (no DDL)  8 DML   NO-DDL  (schema_N == schema_N+1)
```

A migration that alters no tables, columns, indices or keys cannot change the schema. Therefore the
schema at version 25 is structurally identical to the schema at version 26.

## How this file was produced

Exactly one line differs from `26.json` — line 4:

```
26.json:     "version": 26,
25.json:     "version": 25,
```

`scripts/audit/reconstruct_v25.ps1` asserts that exactly one occurrence of the version line exists
and then performs a single string replacement. It verifies the result has an identical line count
(1833) and that exactly one line differs. `identityHash` is intentionally left identical to 26's,
because the structure is identical.

## Why this reconstruction is trustworthy rather than assumed

The migration test does not take the premise on faith. `RoomMigrationTestHelperTest` creates the
database from this file, runs the real `MIGRATION_25_26`, and then calls
`runMigrationsAndValidate(..., validateDroppedTables = true)`, which validates the resulting
database against the **compiler-generated** `26.json`.

If the premise were wrong — if the real v25 schema differed from v26 in any way — the migrated
database would fail that validation. Room would report a schema mismatch. The test therefore
discriminates between "v25 ≡ v26" and "v25 ≠ v26".

## What this file must not be used for

It must not be presented as compiler evidence, and it must not be used to justify a claim that
versions 1–24 are covered. `RoomMigrationTestHelperTest` records those as **NOT RECONSTRUCTABLE**.

When a genuine future migration runs on a real device, Room will emit a new `N.json` for the new
version. At that point the honest record for 25 becomes compiler-generated and this note should be
retired.
