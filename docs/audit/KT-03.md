# Audit Finding KT-03: Locale-Sensitive Number Formatting Across Exports & UI

## 1. Hypothesis
Numerical formatters (`String.format`, `Double.format()`, etc.) across UI screens, PDF generation, DXF export, and diagnostic logging may implicitly rely on the device's default locale (`Locale.getDefault()`) instead of deterministic `Locale.US`. In European or Arabic locales where comma (`,`) or Eastern Arabic numerals are standard, this could produce malformed CAD files, non-standard engineering reports, or parsing bugs.

## 2. Evidence
1. **AutoCAD DXF Exporter (`app/src/main/java/com/example/sld/SldDxfExporter.kt:34-35, 90-92`):**
   **Strictly Deterministic.** DXF requires period decimal delimiters per AutoCAD AC1009 specifications. The exporter mandates `Locale.US`:
   ```kotlin
   // Locale.US float formatter - MANDATORY for valid DXF group code values
   fun formatFloat(value: Float): String =
       String.format(Locale.US, "%.3f", value)
   ```
   All coordinate, dimension, and angle outputs enforce `Locale.US`.
2. **Engineering PDF Generation (`app/src/main/java/com/example/pdf/Sections.kt`):**
   **Default Locale Leakage.** PDF table generators universally invoke `"%.1f".format(value)` and `"%.2f".format(value)` without specifying `Locale.US`:
   - Line 50: `"Design kVA" to "%.1f".format(gen.designCapacity)`
   - Line 62: `"Governing Current" to "%.1f A".format(ats.governingCurrent)`
   - Line 122-124: `Max Cumulative Voltage Drop: ${"%.2f".format(maxVd)} %`
   - Lines 185-192: `"%.1f".format(circuit.loadKVA)`, `"%.2f".format(it)`
   - Lines 517-521: `"%.2f Ω".format(earthing.singleRodResistance_ohm)`
   In French, German, or Arabic environments, these format calls emit comma decimal separators (`12,5 A`, `3,28 %`, `0,149 Ω`), causing visual inconsistency in official engineering calculation deliverables.
3. **Quick Tool UI Screens (`app/src/main/java/com/example/ui/screens/QuickToolScreens.kt`):**
   **Explicit Locale.US.** UI display formatters in `QuickToolScreens.kt` consistently use `String.format(Locale.US, "%.2f", ...)` (e.g. lines 335, 419, 481, 619, 746, 873, 997).
4. **Owner Decision Dependency (`docs/audit/DECISIONS.md:15`):**
   - Topic `D7`: `Number locale policy (KT-03)` — status `PENDING OWNER DECISION`.

## 3. Impact
- **DXF CAD Exports:** Compliant and safe (`Locale.US` strictly enforced).
- **PDF Deliverables:** Compromised on non-US locales. Engineering calculation sheets will display comma decimal marks or localized digits depending on system language, conflicting with standard electrical engineering notation (IEC/IEEE) where dot decimals are expected on technical reports.

## 4. Classification
**CONFIRMED**

## 5. Proposed Severity
**R1** (Engineering Document Quality / Internationalization; PDF reports drift depending on device locale).

## 6. Recommended Action / Decision
- Align with owner decision **D7**: enforce `Locale.US` for all engineering numerical formatting in PDF generation, DXF exports, and machine-readable data.
- Update `app/src/main/java/com/example/pdf/Sections.kt` to define an extension helper `private fun Double.formatEng(pattern: String = "%.2f") = String.format(Locale.US, pattern, this)` across all PDF sections.

## 7. Files a Fix Would Touch
- `app/src/main/java/com/example/pdf/Sections.kt` (not protected)
- `app/src/main/java/com/example/pdf/PdfReportService.kt` (not protected)
