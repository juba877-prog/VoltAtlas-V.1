# Audit Finding KT-06: String-Typed Domain State Governing Engineering Logic

## 1. Hypothesis
Critical electrical domain concepts (phase systems, conductor materials, insulation types, conduit materials, earthing systems) may be represented as raw, unconstrained `String` primitives in Room entities and engine models. Branching logic based on string comparisons or substrings (`contains("3P")`, `startsWith("3")`, `== "Cu"`) creates fragility against casing, whitespace, and localization variations.

## 2. Evidence
1. **`app/src/main/java/com/example/engine/CableSizingEngine.kt:521, 610, 617, 645, 886-889`**
   Core electrical calculations branch on raw string parsing and ad-hoc substring heuristics:
   ```kotlin
   // Line 521: Substring heuristic to detect 3-phase systems
   val isThreePhase = circuit.phases.trim().uppercase().contains("3P")

   // Line 610: Prefix check for harmonic factor
   val harmonicPhaseFactor = if (circuit.isHarmonic && circuit.phases.trim().startsWith("3")) 0.86 else 1.0

   // Line 617: String comparison for material
   val cableMaterial = if (isAl && !isCu) "Al" else "Cu"

   // Lines 886-889: Adiabatic k-factor selection via chained string equality
   when {
       cableMaterial == "Cu" && insulation == "XLPE" -> 143.0
       cableMaterial == "Al" && insulation == "XLPE" -> 94.0
       cableMaterial == "Cu" && insulation == "PVC" -> 115.0
       cableMaterial == "Al" && insulation == "PVC" -> 76.0
       else -> 115.0
   }
   ```
2. **`app/src/main/java/com/example/engine/ConduitFillEngine.kt:247-249` (Defect P1-8)**
   A string comparison defect in protected engine code causes material filtering to become a no-op:
   ```kotlin
   it.conduitType.trim().equals(input.conduitType.trim(), ignoreCase = true) || input.conduitType == "Rigid PVC"
   ```
   Because `input.conduitType` is a string, `"Rigid PVC"` evaluates the disjunction to `true`, erroneously selecting EMT or GI metallic conduits for PVC queries.
3. **`app/src/main/java/com/example/data/Entities.kt:20-65` (`CircuitEntity`)**
   Entities persist free-form strings rather than type-safe Room enums:
   ```kotlin
   var phases: String = "3P+N+E",
   var cableMaterial: String = "Cu",
   var cableInsulation: String = "XLPE",
   var installation: String = "Perforated cable tray",
   var earthingSystem: String = "TN-S",
   ```
   If a user imports data or enters `"3-Phase"` or `"3 Phase"` instead of `"3P"`, `.contains("3P")` evaluates to `false`, silently defaulting the circuit to a 1-phase calculation ($V_{ph} = 230\text{ V}$ instead of $\sqrt{3} \times 400\text{ V}$).

## 3. Impact
- **Silent Formula Miscalculations:** Variations like `"3 Phase"` or `"Three-Phase"` evade `.contains("3P")`, resulting in erroneous neutral and line current computations without triggering validation errors.
- **Maintenance Complexity:** Without Kotlin sealed interfaces or enums, exhaustive `when` expressions cannot be checked by the compiler (`@OptIn` / compiler warning on missing branches is impossible).
- **Engine Freezing Constraint:** Because `CableSizingEngine.kt` and `ConduitFillEngine.kt` are frozen Tier F files, migrating domain entities to strongly-typed enums requires unfreezing the engine or maintaining an adapter layer.

## 4. Classification
**CONFIRMED**

## 5. Proposed Severity
**R1** (Architecture & Reliability; risk of silent calculation error when encountering non-standard string variants).

## 6. Recommended Action / Decision
- Introduce strongly-typed Kotlin domain enums with Room `@TypeConverters`:
  - `enum class PhaseSystem { THREE_PHASE_FOUR_WIRE, THREE_PHASE_THREE_WIRE, SINGLE_PHASE }`
  - `enum class ConductorMaterial { COPPER, ALUMINUM }`
  - `enum class InsulationType { XLPE, PVC }`
- In the short term, normalize raw string inputs at entity ingestion (`CircuitEntity.phases.canonicalPhaseSystem()`) before passing data to calculation engines.
